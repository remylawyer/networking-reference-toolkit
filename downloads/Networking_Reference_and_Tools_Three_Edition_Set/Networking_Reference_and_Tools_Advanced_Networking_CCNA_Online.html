1.8 VLAN and trunk reminders

• Access port: normally places an endpoint into one data VLAN.

• Trunk: carries multiple VLANs, usually using 802.1Q tags.

• Allowed VLAN list: VLANs permitted across a trunk; VLAN existence and spanning-tree state still matter.

• Native VLAN: untagged frames on an 802.1Q trunk are associated with the configured native VLAN on platforms using this model.

• Native VLAN mismatches can cause traffic to land in the wrong VLAN or trigger warnings.

• Inter-VLAN communication requires Layer 3 routing and suitable policy.

• An SVI is a virtual Layer 3 interface associated with a VLAN; its operational state depends on platform and VLAN/port conditions.

1.9 Routing reminders

• A router chooses a route using the destination IP and its routing table.

• Longest-prefix match generally selects the most specific matching route.

• A default route is used when no more specific route matches.

• A route existing in the table does not prove the full path or return path works.

• Check interface status, next-hop reachability, route source, ACLs/firewalls, and return routing.

1.10 Wi-Fi essentials

• SSID is the network name; it is not itself proof of authentication or internet access.

• Signal strength, interference, channel utilisation, distance, walls, client capability, and AP placement all affect performance.

• Strong signal bars do not guarantee gateway, DNS, or internet reachability.

• Authentication/encryption settings must match client and access point requirements.

• Compare wired and wireless results to isolate a radio-specific problem.

2. Troubleshooting playbooks

2.1 One device has no connectivity

☐ Record exact error and determine whether other devices are affected.

☐ Check adapter enabled state, cable/link lights, Wi-Fi association, and airplane mode.

☐ Inspect IP address, mask/prefix, gateway, and DNS.

☐ Look for an unexpected subnet or 169.254.x.x IPv4 address on Windows.

☐ Test the gateway, then a known remote IP, then a domain name.

☐ Compare with a working device on the same network.

☐ Make one evidence-based change and repeat the original test.

2.2 Wi-Fi connected but internet unavailable

☐ Check whether one or all devices on the SSID are affected.

☐ Confirm correct SSID and whether a captive portal is required.

☐ Inspect client addressing and test the gateway if permitted.

☐ Test a remote IP and DNS name separately.

☐ Check VPN/proxy settings and the router/AP uplink.

☐ If multiple clients fail, investigate shared equipment, DNS, or ISP service.

2.3 DHCP or wrong IP configuration

☐ Inspect address, prefix/mask, gateway, DNS, DHCP status, and lease details.

☐ Confirm link and VLAN before blaming the DHCP server.

☐ Check scope exhaustion, exclusions, reservations, relay/IP helper, and server availability.

☐ Renew the lease only when appropriate and compare before/after settings.

☐ Avoid arbitrary static IPs; check the address plan and possible conflicts.

2.4 Website fails by name

☐ Check spelling and service availability.

☐ Use nslookup to inspect the result and answering DNS server.

☐ Compare with an approved resolver or known-good device.

☐ Check VPN DNS, local resolver settings, filtering, and records.

☐ Clear local DNS cache only when stale cache is a plausible cause.

☐ A raw-IP browser test may be invalid because HTTPS hosting often depends on the hostname.

2.5 Slow or intermittent network

☐ Record time, affected apps/devices, and whether wired devices are affected.

☐ Separate latency, packet loss, throughput, and DNS delay.

☐ Compare near the access point versus the usual location.

☐ Inspect Wi-Fi interference, channel congestion, link speed, interface errors, and cables.

☐ Check heavy transfers as a controlled comparison.

☐ Treat ping/traceroute as clues; ICMP may be filtered or deprioritised.

2.6 VLAN or trunk issue

☐ Confirm access-port VLAN and VLAN existence/active status.

☐ Check trunk state and allowed VLAN list along the entire path.

☐ Check native VLAN configuration when untagged traffic is involved.

☐ Verify host IP/mask and expected gateway.

☐ Confirm the SVI/router interface exists and is operational.

☐ Then investigate routing, ACLs/firewalls, and return path.

2.7 Local network works; remote networks fail

☐ Confirm the destination is off-subnet according to the host mask.

☐ Inspect the default route and gateway.

☐ Test gateway reachability and inspect router routes if authorised.

☐ Check ACL/firewall policy, NAT where relevant, upstream routing, and return path.

☐ Use traceroute as supporting evidence, not proof of the exact fault.

2.8 A service port appears unreachable

☐ Confirm the destination name/IP and expected service port.

☐ Check whether the server is running and listening on that port.

☐ Test network reachability and TCP port connectivity from an authorised client.

☐ Check host firewall, network firewall, ACLs, NAT/port forwarding, and routing.

☐ Confirm the application binds to the expected interface and protocol.

☐ A successful TCP connection does not prove the application is healthy or secure.

Escalate when: impact is broad or increasing, a security incident is suspected, the fault involves shared infrastructure, the next action needs unapproved privileges/changes, or rollback is uncertain. Include scope, start time, evidence, tests and changes already attempted.

2.10 Worked troubleshooting examples and self-check

The outputs below are illustrative examples, not captured results. Real wording and available fields vary by operating system, device, and software version. Use only on systems you are authorised to troubleshoot.

Example A: Windows has a 169.254.x.x address

Illustrative result: IPv4 Address . . . . . . . . . . : 169.254.23.8; Default Gateway . . . . . . . . . : (blank).

Interpretation: Windows commonly uses an IPv4 link-local address when it has not obtained a DHCP lease. Check link/Wi-Fi association, VLAN, DHCP scope, relay/IP helper, and DHCP server path. Do not conclude that the DHCP server itself is faulty until the link and VLAN path have been checked. A manually configured address is an exception to this clue.

Example B: IP connectivity works but name lookup times out

Illustrative tests: ping 192.168.10.1 returns replies; nslookup portal.example.test times out against the configured DNS server.

Interpretation: the gateway test suggests local IP connectivity is working, but ping can be filtered and does not prove every service works. The DNS timeout directs the next investigation toward the configured resolver, DNS server reachability, UDP/TCP 53 policy, VPN DNS settings, and resolver service. Do not replace the hostname with an IP in a browser as a definitive test: HTTPS certificates and virtual hosting commonly depend on the hostname.

Example C: One VLAN cannot reach another

Check in order: client address and prefix → access VLAN → VLAN existence and trunk allowed list → SVI/router interface status → route and ACL/firewall policy → return path. If same-VLAN communication works but cross-VLAN communication fails, Layer 3 routing or policy becomes a stronger hypothesis, but verify the full path before changing configuration.

Self-check questions

  1. A client has 169.254.8.4/16 and no gateway. Name two checks to perform before changing the address manually.

  2. A host can ping its gateway but cannot resolve a domain. Which service should you investigate next, and why is this not absolute proof of a DNS-only fault?

  3. Two hosts in the same VLAN communicate, but a host in another VLAN cannot reach them. Name three checks in a sensible order.

  4. Why is a failed ping not enough to conclude that a remote application is down?

  5. What should be recorded before and after a configuration change?

Answer key

  • Check physical/Wi-Fi link and the expected VLAN; inspect DHCP lease/status, scope capacity, relay/IP helper, and server path.

  • Check the configured DNS resolver and name-resolution path. A ping can be filtered, the DNS server may be unreachable, and other policies or application issues may coexist.

  • Check the source host address/prefix, switch access VLAN and trunk path, then SVI/router interface and routing/ACL policy; verify the return path.

  • ICMP may be filtered or deprioritised, while the application uses a different protocol/port. Test the actual service using an authorised method.

  • Record symptoms, scope, baseline output, intended change, approval/rollback plan, commands/actions, verification results, and remaining issues.

3.8 Subnet calculator logic

For IPv4, a prefix /n means n network bits and 32−n host bits. For a conventional subnet, total addresses = 2^(32−n); usable hosts are usually total−2, except special cases such as /31 point-to-point links and /32 host routes.

3.8 Subnet calculator logic
Input Example
IPv4 address 192.168.10.77
Prefix /26
Network address 192.168.10.64
Broadcast address 192.168.10.127
First / last host 192.168.10.65 / 192.168.10.126
Total / conventional usable 64 / 62

• For real network planning, validate input format and prefix range (IPv4 prefix 0–32).

• Check that a proposed gateway lies inside the subnet and is not the network or broadcast address for conventional subnets.

• Check overlap against existing routes, VPNs, cloud VPC/VNets, and remote sites.

• Do not trust a calculator output without understanding whether it treats /31 and /32 specially.

4. Concept and protocol reference

IP addressing and subnetting

Function: Gives interfaces logical addresses and defines which destinations are local versus routed.

Related systems: IPv4/IPv6, subnet masks/prefixes, gateways, routes, DHCP.

Remember: The mask/prefix affects the host’s local-versus-remote decision.

Ethernet switching

Function: Moves frames inside a Layer 2 network using MAC learning and VLAN context.

Related systems: MAC address table, access ports, trunks, STP, ARP.

Remember: A switch does not automatically route between VLANs.

Routing

Function: Chooses a path for packets between IP networks.

Related systems: Routing table, connected/static/dynamic routes, next hop, longest-prefix match.

Remember: Forward path and return path both matter.

ARP and IPv6 NDP

Function: Discover local-link neighbours for packet delivery.

Related systems: ARP for IPv4; ICMPv6 Neighbor Discovery for IPv6.

Remember: For a remote IPv4 host, a client normally resolves the gateway’s MAC—not the remote host’s MAC.

TCP and UDP

Function: Transport application data between process endpoints.

Related systems: Ports, sockets, TCP handshake/retransmission, UDP datagrams.

Remember: Port reachability is not the same as application health.

VLANs and trunks

Function: Separate Layer 2 broadcast domains and carry VLAN traffic between switches.

Related systems: 802.1Q tags, access ports, native VLAN, SVIs, inter-VLAN routing.

Remember: VLANs are logical segmentation, not a complete security boundary by themselves.

NAT/PAT

Function: Translates addresses and often ports between address domains.

Related systems: Private/public IPv4, connection tracking, port forwarding.

Remember: NAT is not encryption and does not replace firewall policy.

Firewalls and ACLs

Function: Enforce traffic policy based on rules and connection context.

Related systems: Stateful inspection, source/destination, protocol, port, rule order, logs.

Remember: A rule should be least-privilege, documented, and tested.

VPN

Function: Creates an encrypted or otherwise protected logical connection across another network, depending on VPN type.

Related systems: IPsec, TLS-based VPNs, routes, DNS, identity and MFA.

Remember: A connected VPN can still have incorrect routes or DNS.

Network monitoring

Function: Collects telemetry and logs to show health, trends, and faults.

Related systems: SNMP, syslog, flow records, metrics, alerts, time synchronisation.

Remember: Good monitoring needs baselines and actionable alerts, not just data volume.

Cloud VPC/VNet

Worked example: how a host reaches a website

Example network: client 192.168.10.77/26, default gateway 192.168.10.65, and a website hostname that resolves to a remote IP address. This is a conceptual example; the actual path depends on DNS, routing, firewalls, and the service design.

  1. The client checks the destination against its own IPv4 prefix. If the destination is outside 192.168.10.64/26, it sends the packet to its default gateway.

  2. If the gateway MAC address is not already cached, the client uses ARP to learn the local-link MAC address for 192.168.10.65. It does not ARP for the remote website server across the internet.

  3. The client sends an Ethernet frame to the gateway MAC. The IP packet still has the remote server as its destination; the router examines the destination IP and selects a route.

  4. DNS resolution is a separate dependency: the client or its resolver must obtain an appropriate record. A cached answer may mean no new DNS query is needed.

  5. Routers and security devices forward or filter traffic according to routes and policy. Replies also need a valid return path. HTTPS additionally depends on successful TLS negotiation and the correct hostname/certificate.

Key distinction: Ethernet source/destination MAC addresses are local-link delivery information and may change at each routed hop; the IP source/destination generally remain end-to-end unless NAT or another translation changes them.

5. Advanced and CCNA-focused reference

These modules add the switching, routing, security, and automation topics that commonly appear in CCNA-level study. Practise in a simulator or authorised lab before using commands on production equipment.

5.1 Spanning Tree Protocol (STP/RSTP)

Spanning Tree prevents Layer 2 loops when redundant switch links exist. Switches exchange BPDUs and select a root bridge; other switches choose paths toward that root. RSTP converges faster than classic STP in typical supported designs.

  • Root bridge: the switch selected as the reference point for the spanning-tree topology. Lower bridge ID wins; priority is considered before MAC address.

  • Root port: the best path from a non-root switch toward the root bridge.

  • Designated port: the forwarding port selected for a network segment.

  • PortFast is intended for edge/access ports connected to end devices, not switch-to-switch links. BPDU Guard can disable an edge port if it receives a BPDU; apply according to the network design.

Useful verification: show spanning-tree, show spanning-tree vlan <vlan-id>, show interfaces status. Confirm the root bridge, port roles/states, and whether the observed topology matches the intended design.

5.2 EtherChannel and link aggregation

EtherChannel groups compatible physical links into one logical link. LACP is a standards-based negotiation protocol; PAgP is Cisco-proprietary. The member links must have compatible settings, including speed/duplex where applicable, access/trunk mode, VLAN settings, and channel parameters.

Useful verification: show etherchannel summary, show interfaces port-channel, show interfaces trunk. If a member is suspended or excluded, compare its configuration with the other members and inspect the negotiation state.

5.3 Routing decisions and OSPF fundamentals

A router first chooses the most specific matching route (longest-prefix match). When competing routes have the same prefix length, route source preference and metric help determine the selected route. A default route is used when no more-specific match exists.

OSPF is a link-state interior gateway protocol. Routers form neighbour adjacencies, exchange link-state information, and calculate shortest paths. In a simple CCNA lab, begin with OSPFv2 in a single area, commonly area 0; learn neighbour formation and advertised networks before adding complexity.

Useful verification: show ip route, show ip protocols, show ip ospf neighbor, show ip ospf interface, show ip route ospf. Check interface addressing, area settings, network statements or interface-level OSPF settings, timers/authentication where configured, and whether the expected routes are installed.

5.4 IPv6 addressing and neighbour discovery

IPv6 uses 128-bit addresses. Learn global unicast, link-local, unique local, multicast, and loopback addresses. Link-local addresses are used on the local link and are not routed across routers. IPv6 uses Neighbor Discovery Protocol (NDP), rather than ARP, for neighbour discovery and related local-link functions.

  • SLAAC allows a host to form its own address using router advertisements; DHCPv6 can provide additional or managed addressing information depending on the design.

  • A default route and correct Layer 3 reachability still matter; an assigned IPv6 address alone does not prove end-to-end connectivity.

  • Useful verification: show ipv6 interface brief, show ipv6 route, ping, and traceroute/tracert with IPv6-aware options where supported.

5.5 ACLs, NAT/PAT, and device security

Access control lists are evaluated in order, with the first matching entry determining the result; an implicit deny exists at the end of an ACL. Standard IPv4 ACLs primarily match source IPv4 addresses; extended ACLs can match protocol, source/destination addresses, and ports. Placement depends on the policy and traffic direction.

NAT translates addresses; PAT allows multiple internal sessions to share an outside address by tracking transport-layer ports. Do not assume NAT itself is a security policy or firewall. Confirm translations, routes, ACLs, and return traffic separately.

Useful verification: show access-lists, show ip interface, show ip nat translations, show ip nat statistics, show running-config sections relevant to the feature. For device management, prefer SSH over Telnet, use individual accounts/AAA where appropriate, and restrict management access.

5.6 First-hop redundancy and resilient design

First-hop redundancy protocols provide a virtual default-gateway address that can remain available if one gateway device fails. HSRP is a common Cisco example; VRRP is an open standard. Redundancy improves availability only when the failure modes, tracking, Layer 2 path, and upstream routing are designed and tested correctly.

When troubleshooting, verify the active/standby state, virtual IP, interface status, tracking configuration, and whether clients are using the intended default gateway. Avoid making changes during a live incident without an approved plan.

5.7 Wireless, network access, and automation

For enterprise wireless, distinguish the client, access point, wireless LAN controller (where used), SSID, authentication method, VLAN mapping, and wired uplink. A client can associate to Wi-Fi yet fail to obtain an address or reach services because later stages are broken.

Common access-layer protections include port security, DHCP snooping, Dynamic ARP Inspection, and BPDU Guard. Each has prerequisites and can interrupt legitimate traffic if deployed incorrectly; learn the threat addressed, trust boundaries, and verification commands before enabling it.

Network automation fundamentals include structured data such as JSON, REST APIs, controller-based management, and configuration templates. Automation reduces repetitive work but can also repeat a mistake quickly; use version control, test environments, least privilege, and reviewable change plans.

Wireless performance and authentication

  1. Establish scope: affected clients, APs, SSIDs, locations, time pattern and recent changes.
  2. Measure/inspect signal quality, SNR if available, band, channel utilisation, interference, roaming, client capability and AP placement.
  3. Compare near-AP tests, alternate clients and wired performance; distinguish PHY/radio issues from DHCP, DNS, gateway, proxy, VPN and application issues.
  4. Correlate client logs and driver/firmware state with AP/controller events. For enterprise authentication, check EAP method, certificate chain/validity/time, identity/policy, RADIUS reachability and server-side rejection logs.
  5. Apply one approved change at a time, record baseline and define rollback criteria before altering channels, transmit power, security or firmware.

WPA2-Personal uses a shared passphrase. WPA2-Enterprise uses 802.1X/EAP and typically a central authentication service such as RADIUS. Use supported current security settings (WPA3 where compatible) and the organisation's policy.

7.3 Routing case: route exists, traffic still fails

Scenario: a branch router has a route to 10.40.8.0/24, but clients cannot reach the application. Check the route's source, next hop and administrative/metric selection; verify next-hop reachability and ARP/ND; confirm the egress interface and policy; then validate the return route from the destination network. Test the exact transport and port, not just ICMP. Consider asymmetric routing, stateful firewall expectations, NAT, MTU/PMTUD and application-layer TLS/authentication only where evidence points there.

Reasoning rule: routing-table presence means a forwarding decision can be selected for a destination prefix; it does not prove that the next hop is alive, that packets traverse policy, that the return path exists, or that the application responds.

7.4 ACL and firewall reasoning

  • Write a flow tuple before editing policy: source, destination, protocol, source/destination port, direction, interface/zone and expected state.
  • Check rule order, implicit deny, object groups, address translation order, established/return traffic, logging and hit counters.
  • Evaluate both forward and return paths. A rule that permits one direction may not satisfy stateful inspection or routing requirements.
  • Prefer a narrow, time-bounded rule with an owner and rollback plan over broad “permit any” troubleshooting changes.
  • Confirm the application actually listens on the target address/port and inspect service logs; a network policy may not be the fault.

7.5 OSPF and neighbour failure checklist

When an OSPF adjacency is absent or unstable, compare area, network type, timers, authentication, subnet/mask, MTU, router IDs, passive-interface settings and reachability of the directly connected peers. Inspect logs and neighbour state before clearing processes or changing timers. An adjacency state alone does not guarantee that the required prefixes are advertised, accepted, installed and selected.

7.6 EtherChannel and trunk scenario

One member link forwards but the bundle is degraded. Check that both ends agree on channel protocol and member settings, speed/duplex, trunk/access mode, allowed VLANs, native VLAN, and Layer 2/Layer 3 mode. Verify that members are actually bundled rather than suspended or individual. Do not remove members or renegotiate a production bundle without an approved change plan.

7.7 IPv6 fault isolation

  1. Confirm the interface has the expected link-local address and any intended global/ULA address.
  2. Inspect Router Advertisements, prefix flags, default route and the expected SLAAC/DHCPv6 design.
  3. Check the neighbour cache and ICMPv6 messages; do not apply an IPv4-only troubleshooting model.
  4. Test DNS AAAA and A answers separately, and determine which address family the application actually selected.
  5. Review firewall rules, routing and return path for IPv6 independently of IPv4.

7.8 Automation and change safety

For scripts or Ansible, define inventory scope explicitly, start with read-only facts/show commands, protect credentials in an approved secrets mechanism, capture before/after state, use version control, and test on a lab or small canary set. Add timeouts and failure handling; do not assume a command is idempotent merely because it is automated. Keep secrets and sensitive configurations out of public repositories.

7.10 Escalate before a risky intervention

Escalate suspected compromise, broad outages, routing instability, possible data exposure, changes affecting shared infrastructure, unknown production dependencies, or work requiring privileges/maintenance windows outside your authority. Preserve evidence and avoid “fixes” that destroy logs or conceal the timeline.
